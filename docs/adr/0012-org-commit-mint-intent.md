# Org Commit mint is explicit client intent; instance id is server-evaluated after transform

Inferring “start new” from an empty `jobInstanceId` or provisional UI state made mid-Job commits ambiguous and let wire sentinels leak into Domain.

**Decision:** Commit carries explicit mint intent: `startingNew` or `none` (omit ⇒ `none`). The server never infers mint from an empty instance id, first-Task position alone, or client provisional state. **`startingNew`** mints a Job instance on the first leaf Task in authored Job order: client sends empty instance id (any client id is ignored); after transform, the server evaluates Config instance id/label expressions, appends the instance, and returns the evaluated id—the SPA rebinds from that response. A second `startingNew` that would mint the same evaluated id is rejected. **`none`** continues an existing instance (real id required) and never mints. Wire sentinel `_new` is rejected. Provisional “start new” UI is client-only until the first successful `startingNew` Commit; there is no separate create route. Task-group mint (`spawningNew`) is removed with groups ([ADR-0008](0008-org-task-submit-cardinality.md)); flat many-submit uses `none` + real Job instance ids.

**Considered options:** Infer mint from empty id; accept `_new` as please-mint; client-supplied instance id on first Commit; mint from Worklist alone without `mint` on the body. Rejected for ambiguity, Domain pollution, and keeping id law in Config exprs after transform with Commit as the Seam.
