# Resources have event-driven lifecycles

The Interpretation package is authored as **resource types with lifecycles** (and scope types, ADR-0010) and **event types** that move them between states, not as Jobs and Tasks whose forms carry arrays of rows. A resource's **state is derived by the engine** from the events that happened to it; no event or expression writes it. Each state declares the properties a resource must have in it (`requires`); events gain or update properties and never remove them. A **correction** supersedes an earlier Observation and the state is recomputed; corrections are not transitions. The model is described in [`docs/interpretation-package.md`](../interpretation-package.md).

We chose this because the current authoring model stores lifecycle as flags that config writes (`fullyProcessed`, pallet `progress`, container `incomplete`) and pushes everything that repeats into array or dynamic-map Task forms. In the Feragame config that forces cell-map projection, untouched-row filtering, continuation prefills, supersede maps, and repeatable groups that exist only to allow another submit (`line/lineLoad/mark`, `line/containerReg/register`). A state derived from events is replayable by construction, which the target architecture requires (`docs/vision.md`, Reconstruction), and `requires` lets the registry reject a package whose event types cannot reach a state with the properties it needs.

**Considered options:** (1) Keep Tasks with array forms — rejected: the complexity above lives in config and in engine special cases, and one row cannot be corrected or resubmitted on its own. (2) State as an ordinary property that events set, as in the first sketch — rejected: nothing stops two events from disagreeing, and the package cannot be checked. (3) States that add *and remove* properties — removal rejected: history keeps every value, so "absent in this state" is a presentation of the state, not a deletion. (4) Corrections as reverse transitions (`done` back to `partially_loaded`) — rejected: every resource type would need undo edges for moves that never happen physically.

**Consequences:** The engine needs state derivation from events and a package validator for `requires`. This replaces Task authoring, which ADR-0005 and ADR-0006 build the worklist and operator routes on; both need reopening. ADR-0007 uses the Job instance as the passport subject; under this model the subject is a resource.
