# Living Worklist is server-projected; SPA does not re-gate

Unlock order and startsWhen for the operator UI are evaluated only in Go from **Submission** relations and shipped as a **Worklist** on living Load and Commit. A Task is `done` after Submission on the instance (Domain reads fill forms; they do not reopen Worklist status). The SPA reads Task statuses (`locked` | `unavailable` | `available` | `actionable` | `done`) and Job `canStart`; it must not re-implement those rules (no production TS Unlock/startsWhen, readyWhen, or Domain-read / row-id twins). This reverses the flat-port “copy pure Unlock/startsWhen into `app/` for chrome” policy: Commit remains Cerbos-authoritative, but chrome affordances are a Go projection, not a second rule body.

Once full Org Config leaves the wire, each Worklist Job also carries chrome metadata the SPA cannot invent: authored `taskIds` order, `startLabel`, and `repeatable`. Status vocabulary was `locked` | `available` | `done` only (see amends below for `actionable` and `unavailable`). **Task form bundle**s (minimum form payload; bindings bag is DomainSnapshot-shaped for live Chrome/Derived) ship for every `available` Task plus provisional start (`jobInstanceId` empty when `canStart`). On Load and successful Commit, Go also evaluates authored Chrome `dataReport` rules (Domain-only; flat or sections DTO) into `bindings.chromeDisplay` (keyed by field id); the SPA paints those results and must not re-aggregate Domain for them. Live Chrome that still needs draft/operator (`readonly`) stays client-side. Load/Commit JSON do not include full Domain or Org Config.

**Amended by [ADR-0006](0006-living-operator-worklist-home.md) (operator home):** home Load omits bulk Task form bundles (`taskFormBundles` empty); Task routes hydrate via addressed `GET /api/living/task-form`. Commit still returns an updated Worklist; auto-advance adds `nextTaskFormBundle` when the same viewer has another role-eligible `available` Task on that instance (otherwise overview/home). The “every `available` bundle on Load” rule above remains the general projection model outside that lazy home path.

**Amended (viewer-scoped status enum):** Worklist Task status on the wire is `locked` | `unavailable` | `available` | `actionable` | `done`. Unlock/Submission law still yields locked / unlocked / done. When unlocked and not done, Go evaluates Task **readyWhen** with the same semantics as Commit (`evaluateReadyWhen` / omit⇒true / fail⇒false). False ⇒ `unavailable` (Worklist chrome; visible, not navigable) and **skips** role split — do not overload `available` (that remains role handoff). Else unlocked splits by Config-role eligibility into `available` (not for this viewer — UI “Disponibile”) vs `actionable` (UI “Per te”; home Available, mount gates, and overview navigation). Home / mount remain **actionable-only** (`unavailable` never appears in Available bands or mount-ok). This replaces the prior split of role-blind `locked|available|done` plus a parallel `viewerAvailable[]` id list — the SPA must not re-derive “mine” from a second channel, and must not twin readyWhen in TS. Group-occurrence aggregate prefers any child `actionable`, else any `available`, else all `done`, else `locked`. Auto-advance / “role-eligible available” language in ADR-0006 means `actionable`.
