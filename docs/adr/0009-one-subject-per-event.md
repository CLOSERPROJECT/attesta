# One subject per event; tables are views

An event type has **at most one subject**: the resource or scope whose lifecycle it advances (scopes per ADR-0010). An event type without a subject must create at least one resource or scope. Scopes and resources that give an event its context (shift, lot on the line, truck) are **references** and are never advanced by it. Applying the same event to many resources is **one event per resource**. A table on the operator's board is a view over one event type: each row is one resource, and a row is sent as its own Observation as soon as it is valid and settled (the operator leaves the row or presses Enter). "Submit all" is an optional per-view setting and still sends one Observation per row. See [`docs/interpretation-package.md`](../interpretation-package.md).

We chose this because one subject means one row, one state transition, and one Observation. Each Observation can then be resent, corrected, and replayed on its own, and offline conflicts stay scoped to a single resource (`docs/vision.md`, Offline capture and sync). Rules that span rows, such as container weights balancing against a lot, become prompts and checks instead of capture gates (ADR-0008, `docs/vision.md`, "Capture is never blocked").

**Considered options:** (1) One event with a set of subjects, such as marking several pallets in one submit — rejected: the Observation would be corrected and conflict as a unit, and rows could not be sent independently. (2) Computing REA `consumes` / `produces` with quantities now — deferred: references plus weights computed from events cover Feragame, and computing flows is better designed against a real transformation, most likely between companies. The flows are declared now (ADR-0010). (3) Array forms in one Task, as today — rejected by ADR-0008. (4) "Submit all" as the default — rejected: operators should not need an extra action to record what they already entered.

**Consequences:** In-between states become visible (some containers weighed, the lot not yet exhausted); this is correct for capture and offline work. Genealogy, such as the weight each lot contributes to a container, is computed from references rather than entered. The GUI needs a generic table view and row-level sending; editing a sent row sends a correction.
