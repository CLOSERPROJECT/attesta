# UNTP linking of input Passports to outputs

Research for [issue 01](../issues/01-untp-input-passport-linking.md). Sources read on 2026-11-19. Every claim in the "Findings" sections links to the primary source that owns it. The [Implications for Attesta](#implications-for-attesta) section is inference and is kept separate.

## Short answer

- **Version.** UNTP has moved. The spec now lives on the UN's GitLab, not on GitHub. The latest tagged release is **v0.7.0** (tagged 2026-05-04), and the site labels it the "latest" version, suitable for pilots. **v1.0 is not released yet.** The work-in-progress draft, which is the 1.0 candidate with artefacts under `v0.8.0`, replaces 0.7.0's own event schemas with **GS1 EPCIS 2.0 events used unmodified**.
- **Event types.** Across the three model generations, the same EPCIS event types do the work. A `TransformationEvent` consumes inputs. An `AggregationEvent` packs things into a container. Shipping and receiving `ObjectEvent`s record the hand-off. An `AssociationEvent` records assembly. In the 1.0 candidate, `TransactionEvent` is not the hand-off event.
- **`ModifyEvent`.** It is a real schema in 0.7.0 (for post-market actions). It does not exist in 0.6.x or in the 1.0 candidate, where the same job is done by an `ObjectEvent`.
- **Identifying inputs.** Inputs are named either by instance-level identifiers (`inputEPCList`) or by a class-level identifier plus a quantity (`inputQuantityList`). EPCIS lets a listed input be "fully or partially consumed". When only part of a batch moves, the 1.0 candidate says to pack that part into a container with its own identifier first, and then name the container.
- **DPP links.** `traceabilityInformation`, `TraceabilityPerformance`, `verifiedRatio` and the `SecureLink` hash fields exist only in 0.6.x. From 0.7.0, a DPP reaches its events and input passports through typed `relatedDocument` links (optionally with `digestMultibase`) and through the Identity Resolver. `materialProvenance` (renamed from `materialsProvenance`) is the issuer's own optional declaration. UNTP does not require it to be derived from the inputs, and it does not want upstream data restated.
- **Who issues.** Each actor issues the events for what it did itself. The consumer issues the transformation. Both sides of a transfer should sign their own half: the supplier signs the shipping event and the buyer signs the receiving event.

Further points from the same sources:

- The choice between the three "bringing together" events is semantic. A transformation consumes its inputs and cannot be undone. An aggregation is temporary and the children keep their identity. An association is lasting ([L159–163](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalTraceabilityEvents.md#L159-163)). The sample that builds a battery from cathode uses a `TransformationEvent`, with the cathode batch as an input quantity and the battery as an output EPC ([cathode_assembled_into_battery](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/artefacts/samples/v0.8.0/dte/DigitalTraceabilityEvent_cathode_assembled_into_battery_instance.json)).
- **`TransactionEvent` is not the inter-org hand-off in the 1.0 candidate.** EPCIS defines it as "the association or disassociation of physical or digital objects to one or more business transactions" ([EPCIS 2.0 §7.4.4](https://ref.gs1.org/standards/epcis/), p. 88). EPCIS also suggests it for loose groupings such as "two pallets that are part of the same shipment" (§7.4.3, p. 83). The UNTP guide does not use it for any of its rows.
- First commissioning of a batch with no traceable input (harvest, mining) is an `ObjectEvent` · `ADD` ([L154](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalTraceabilityEvents.md#L154)).

## How `inputEPCList` / `inputQuantityList` / `outputEPCList` identify inputs

### EPCIS 2.0 definitions (normative for the 1.0 candidate)

- `inputEPCList` is "an unordered list of one or more EPCs identifying (at the instance level) objects that were inputs". `inputQuantityList` is a list of `QuantityElement`s "identifying (at the class level)" inputs. `outputEPCList` and `outputQuantityList` mirror these for outputs ([EPCIS 2.0 §7.4.5](https://ref.gs1.org/standards/epcis/), pp. 93–94).
- A `QuantityElement` is `epcClass` ("a class-level identifier for the class to which the specified quantity of objects belongs"), plus an optional `quantity` and an optional `uom`. Without `uom` the quantity is a count. With `uom` it is a physical measure. If `quantity` is omitted, the quantity is unknown (§7.3.3.1, p. 54).
- A `TransformationEvent` describes objects that "are fully or partially consumed as inputs". It asserts that "any of the inputs may have contributed in some way to each of the outputs" (§7.4.5, p. 93). Listing an input therefore does **not** claim that all of it was used.
- `transformationID` links several `TransformationEvent`s into one transformation. Without it, an event must have at least one input and at least one output (§7.4.5, pp. 93–95).

### What UNTP adds

- Any URI scheme may be used. Identifiers need not be GS1, and schemes may be mixed within one event ([WIP DTE L91](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalTraceabilityEvents.md#L91), [L126–128](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalTraceabilityEvents.md#L126-128)). In GS1 terms, batches are class-level (`lgtin`) and serialised items are instance-level (`sgtin`) ([0.7.0 DTE L450–462](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/versioned_docs/version-0.7.0/specification/DigitalTraceabilityEvents.md#L450-462)).
- TEV-05 / design requirement 06 is answered this way: use `epcList` / `inputEPCList` / `outputEPCList` for instance-level identifiers, and `quantityList` / `inputQuantityList` / `outputQuantityList` for class-level quantities. "Where a batch is split across movements, the moved quantity is first packed into an identified container" ([WIP DTE L96](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalTraceabilityEvents.md#L96)).
- The reasoning: "A batch can be split. A `quantityList` entry only says that some quantity of the batch moved … To move part of a batch unambiguously, pack it first: an `AggregationEvent` places the quantity in a case, pallet or container with an instance identifier of its own, and the shipping and receiving events then name that container" ([L183](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalTraceabilityEvents.md#L183)).
- The samples show the partial-consumption pattern:
  - A refinery packs 2,000 kg out of cathode batch `…/batch/2025-Q1-0812` into a carrier container (`childQuantityList` with the batch as `epcClass`).
  - A battery maker's `TransformationEvent` lists `inputQuantityList: [{epcClass: …/batch/2025-Q1-0812, quantity: 36, uom: KGM}]` and the battery as `outputEPCList`.
  - The cathode DPP is issued once for the whole batch.
  - Sources: [cathode_loaded_into_container](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/artefacts/samples/v0.8.0/dte/DigitalTraceabilityEvent_cathode_loaded_into_container_instance.json), [cathode_assembled_into_battery](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/artefacts/samples/v0.8.0/dte/DigitalTraceabilityEvent_cathode_assembled_into_battery_instance.json), [DigitalProductPassport_cathode_instance](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/artefacts/samples/v0.8.0/dpp/DigitalProductPassport_cathode_instance.json) (`idGranularity: model`, `batchNumber: 2025-Q1-0812`).
- "Whole Passport versus items inside a batch": UNTP has no special "passport as input" construct. An event names product identifiers, and the DPP is reached "by resolving the product or facility identifier through an Identity Resolver" ([WIP DTE L101](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalTraceabilityEvents.md#L101)). The granularity of the identifier is what matters, and the IDR returns inherited links from coarser identifiers ([WIP IDR L964](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/IdentityResolver.md#L964)).
- In 0.7.0, each `EventProduct` pairs a `product` (with `idGranularity` `item` / `batch` / `model`) with an optional `quantity` and a per-product `disposition`, such as `consumed` on inputs ([0.7.0 DTE L80](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/versioned_docs/version-0.7.0/specification/DigitalTraceabilityEvents.md#L80), [L230–252](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/versioned_docs/version-0.7.0/specification/DigitalTraceabilityEvents.md#L230-252)).

## How the DPP points at events, and `materialProvenance`

### 0.6.x only

- `traceabilityInformation` is an array of `TraceabilityPerformance` objects, each with a `valueChainProcess` (string), a `verifiedRatio` (0–1, the "proportion of materials … verifiably traced") and a `traceabilityEvent` array of `SecureLink` objects. A `SecureLink` has `linkURL`, `linkName`, `linkType`, `hashDigest`, `hashMethod` (`SHA-256`/`SHA-1`) and `encryptionMethod` (`none`/`AES`).
- "Each value chain step SHOULD specify the `verifiedRatio` … and MAY include `traceabilityEvent` links."
- Sources: [0.6 DPP L368–396](https://github.com/uncefact/spec-untp/blob/af6cd474186957ad2e8d20bff84f86236e013b2a/website/docs/specification/DigitalProductPassport.md#L368-L396), [untp-dpp-schema-0.6.0.json](https://test.uncefact.org/vocabulary/untp/dpp/untp-dpp-schema-0.6.0.json) `$defs.TraceabilityPerformance`, `$defs.SecureLink`.

### 0.7.0 and WIP

- None of `traceabilityInformation`, `TraceabilityPerformance`, `SecureLink`, `verifiedRatio` or `hashDigest` appears in `artefacts/schema/v0.7.0/dpp/DigitalProductPassport.json` or `artefacts/schema/v0.8.0/dpp/DigitalProductPassport.json` (grep of both schemas at [c7c3bc79](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/tree/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/artefacts/schema)).
- The `credentialSubject` is now `Product` directly. Seven properties are mandatory: `id`, `name`, `idScheme`, `idGranularity`, `productCategory`, `producedAtFacility` and `countryOfProduction` ([WIP DPP L97](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L97)).
- DPP-06 Traceability: "The `relatedDocument` array can link to upstream DPPs and DTE traceability event credentials using typed links" ([WIP DPP L63](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L63); same text in [0.7.0 DPP L62](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/versioned_docs/version-0.7.0/specification/DigitalProductPassport.md#L62)).
- `Link` has `linkURL`, `linkName` (both required), plus `linkType`, `mediaType` and an optional `digestMultibase` "to ensure the content of the link has not changed" (both DPP schemas).
- The `dte` link type is `https://test.uncefact.org/vocabulary/link-type/dte`, meaning "a product or batch, to a digital traceability event about it" ([WIP IDR L33](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/IdentityResolver.md#L33)). Link types MUST be absolute `http(s)` URIs ([WIP DPP L292–294](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L292-294)). Resolvers SHOULD still accept 0.7's `untp:dte`-style aliases ([WIP IDR L39](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/IdentityResolver.md#L39)).
- The DTE is "not fixed into the passport", because "the production record is often commercially sensitive". `includedComponent` (the bill of materials) "is not the manufacturing input list" ([WIP DPP L210–217](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L210-217)).
- "UNTP composes rather than nests. Each actor issues a passport about the product it ships and links to the passports of the inputs it consumed, through Digital Traceability Events … A finished-goods manufacturer is not obliged to restate what its suppliers already asserted" ([WIP DPP L302–308](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L302-308)).
- The v0.8.0 sample DPPs carry no `dte` link in `relatedDocument`. Event discovery in the samples goes through the resolver ([battery DPP sample](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/artefacts/samples/v0.8.0/dpp/DigitalProductPassport_battery_instance.json)).
- Reporting traceability coverage on a claim (the successor idea to `verifiedRatio`) is an open item, tracked in [issue #853](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/issues/853) ([ChainOfCustody L194–196](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/design-patterns/ChainOfCustody.md#L194-196)).

### `materialProvenance`

- It is optional (`Material*`). It lists "the materials it is made of, by origin, mass fraction and recycled content" ([WIP DPP L114](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L114), [L183](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L183)). The 0.6 name was `materialsProvenance` ([0.6 DPP L170](https://github.com/uncefact/spec-untp/blob/af6cd474186957ad2e8d20bff84f86236e013b2a/website/docs/specification/DigitalProductPassport.md#L170)).
- `originCountry` is "the primary production country of that material by mass". A component's origin "is deliberately not copied onto the parent" ([WIP DPP L226–230](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L226-230)).
- The spec does not require `materialProvenance` to be computed from DTE inputs. The cathode sample declares concentrate (ZM, 0.88) and scrap (JP, 0.12), which matches its smelting inputs, but the values are the issuer's own declaration ([cathode DPP sample](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/artefacts/samples/v0.8.0/dpp/DigitalProductPassport_cathode_instance.json)).
- Mass-balance checking needs input grades that "come from the input product's DPP rather than from the event" ([ChainOfCustody L520–522](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/design-patterns/ChainOfCustody.md#L520-522)).

## Who issues the event

- WHO is "the credential `issuer`; `sourceList`, `destinationList`", meaning "the party asserting the event" ([WIP DTE L79](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalTraceabilityEvents.md#L79)).
- In the v0.8.0 sample chain, each actor issues the events for its own activity:
  - The mine issues `packing` and `shipping`.
  - The refinery issues `receiving`, `unpacking`, its smelting `TransformationEvent` and its later `loading`.
  - The battery maker issues the `TransformationEvent` that consumes the refinery's cathode batch.
  - Sources: the `issuer` of each [sample DTE](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/tree/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/artefacts/samples/v0.8.0/dte).
- "**Every transfer should be attested by both parties.** … Where the supplier signs the outbound transfer and the buyer signs the inbound one, both referencing a common shipment identifier and quantity, the input total is fixed by a party other than the one claiming against it" ([ChainOfCustody L167–171](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/design-patterns/ChainOfCustody.md#L167-171)). "The counterparty issues its own arrival event, and reconciliation uses both" ([L464](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/design-patterns/ChainOfCustody.md#L464)). This is a design-pattern page, not a normative MUST.
- A third party records its events against someone else's identifier without re-issuing their DPP. It registers the DTE link with the resolver when authorised ([LinkedLifecycleData L133–139](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/design-patterns/LinkedLifecycleData.md#L133-139); [WIP IDR L567–571](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/IdentityResolver.md#L567-571)).
- The DPP itself "is issued by the shipper of goods" ([0.6 DPP L58](https://github.com/uncefact/spec-untp/blob/af6cd474186957ad2e8d20bff84f86236e013b2a/website/docs/specification/DigitalProductPassport.md#L58); unchanged in [WIP DPP L42](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L42)). The receiving facility "records quantities of input materials consumed and output materials produced as transformation event DTEs" ([WIP ChainOfCustody L153–159](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/design-patterns/ChainOfCustody.md#L153-159)).

## Open uncertainties

- **1.0 is not out.** The WIP DTE model (EPCIS as published) is a draft, and it was still moving as of the 2026-10-30 `main` commit. Only the WIP DTE page calls 0.7.0 "withdrawn". The version config still labels 0.7.0 "latest, for pilots".
- **ISO/IEC 19987.** The GS1 EPCIS 2.0 PDF (Release 2.0, ratified June 2022) does not cite an ISO number. I could not confirm which ISO/IEC 19987 edition corresponds to EPCIS 2.0, because iso.org blocked automated access. UNTP itself now cites GS1 EPCIS 2.0 directly.
- **Wording drift inside the WIP.** The DPP page still says "`ModifyEvent`" and "the UNTP `Make` event or its EPCIS `Association` equivalent" ([L210](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/DigitalProductPassport.md#L210)), which contradicts the DTE page. The DTE page is the more specific source and was updated more recently.
- **jargon.sh vocabularies** are referenced by 0.6 only. 0.7+ publishes its vocabulary at `vocabulary.uncefact.org/untp/` and in the repo's `artefacts/` folder ([0.7.0 DTE L43–45](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/versioned_docs/version-0.7.0/specification/DigitalTraceabilityEvents.md#L43-45)). I used the JSON schemas, not jargon.sh renderings.

## Implications for Attesta

*This section is inference from the findings above, applied to the Feragame → Org B worked example. It is not a citation of UNTP.*

**Target model.** Emit chain DTEs as **EPCIS 2.0 events inside the UNTP VC envelope**. That is valid in 0.7.0, through its EPCIS profile, and it is the only form in the 1.0 candidate, so it survives the 1.0 transition. 0.7.0's native `MakeEvent`/`MoveEvent` would need rewriting in a few months. Attesta's `server/internal/untp` already emits 0.7.0-shaped credentials: a `Product` subject, `ModifyEvent`/`LifecycleEvent`, and the `vocabulary.uncefact.org/untp/` context. The legacy Stream `ModifyEvent` is therefore valid 0.7.0, but semantically it is meant for post-market actions, and it disappears in 1.0, where it becomes an `ObjectEvent` · `OBSERVE`. The `LinkTypeDTE` constant still uses the 0.6-era `…/linkTypes/dte` URI. The current form is `…/vocabulary/link-type/dte`.

**The map's settled line needs a correction.** It says inputs are "linked from the DPP's `traceabilityInformation`". That field exists only in 0.6.x. From 0.7.0, Passport → event links go through `relatedDocument` (link type `dte`) and through the resolver.

**What the Feragame containers are.** In the fixture, `containerReg` creates sorted-material containers (glass powder, plastic, aluminium, and so on) from a lot. A container can also continue from a second lot (`secondarySourceLotId`). In UNTP terms, lot → containers is a **Feragame `TransformationEvent`**: the lot is the input, the containers are outputs, and a shared `transformationID` covers containers that span lots. It is not an aggregation, because the material changes. The lot Passport's snapshot lists the container ids, but a UNTP verifier only follows identifiers and events. The container → lot edge has to appear in a DTE that is discoverable from the container identifier.

**Events in the example, and who issues each:**

| Step | Event | Issuer |
| --- | --- | --- |
| Lot processed into containers | `TransformationEvent` (input: lot; outputs: container ids in `outputEPCList`, with weights in `ilmd` or the snapshot) | Feragame |
| Containers handed to Org B | `ObjectEvent` `OBSERVE` `shipping`, naming the container ids, with `sourceList`/`destinationList` and a shared `bol` reference | Feragame |
| Containers received | `ObjectEvent` `OBSERVE` `receiving`, with the same ids and the same `bol` | Org B |
| Org B's Job consumes them | `TransformationEvent` (inputs: see below; outputs: Org B's Passport subject id) | Org B |

The two shipping/receiving events are the both-sides attestation the chain-of-custody pattern recommends. They are optional for a first cut. Org B's `TransformationEvent` alone already satisfies TEV/requirement 03. If the containers travel on a pallet, add a Feragame `AggregationEvent` `ADD` `packing` and an Org B `AggregationEvent` `DELETE` `unpacking`. A `TransactionEvent` is not needed.

**How Org B's event identifies inputs:**

- **Whole lot.** Feragame's Passport id is a Digital Link with `/21/{lotId}`, which is an instance-level identifier. It can go straight into `inputEPCList`. Under the WIP IDR guidance, credentials SHOULD use the canonical `https://id.gs1.org/01/{14-digit GTIN}/10/{FIR}/21/{lotId}` form, with the GTIN padded (`09506000134352`), rather than the deployment host ([WIP IDR L962](https://opensource.unicc.org/un/unece/uncefact/spec-untp/-/blob/c7c3bc79447c9f3934d67ccfcd4ab52447d42d52/website/docs/specification/IdentityResolver.md#L962)). Attesta Passports currently use the deployment origin. Org B's event and Feragame's Passport must use the same string for verifiers to join them.
- **Container level (the expected Org B case: some containers across N lots).** Mint stable URIs for containers and list them in `inputEPCList`. Containers do not need their own Passport. Each container URI does need to resolve to a linkset that reaches the lot Passport(s), through a `dpp` link, a `dte` link to Feragame's lot → container transformation, or both. EPCIS's "fully or partially consumed" covers using only part of a container.
- **Quantity of a lot.** `inputQuantityList: [{epcClass, quantity, uom: "KGM"}]` needs a class-level id. In GS1 terms that is `/01/{gtin}/10/{lot}`, without `/21/`. Feragame's Passport id is item-level, so using it as `epcClass` would be semantically wrong. The 1.0 candidate's own answer for a partial lot is "pack it into an identified container first", which is the container case above. Org B's raw material is sorted containers, not the incoming load, so container level is both the honest and the idiomatic path.

**What Org B's DPP must contain (1.0 candidate):**

- The seven mandatory `Product` fields.
- `relatedDocument` entries pointing at Org B's own `TransformationEvent` credential (link type `dte`).
- Optionally, direct links to each upstream Feragame Passport (link type `dpp`), each with a `digestMultibase`. The digest is the UNTP-native way to pin the frozen upstream snapshot Org B inherited.
- Org B's resolver linkset for its identifier should also expose the `dte` link.

**What Org B's DPP should not do:**

- Restate Feragame's claims or snapshot as its own data. UNTP composes rather than nests. The inherited snapshot belongs in Attesta's internal model and HTML view. In the credential it is a link plus a digest.
- Carry `traceabilityInformation` or `verifiedRatio`. Those are 0.6-only.

`materialProvenance` is optional, and Org B may derive it from its inputs if it wants to.

**Granularity mismatch to settle separately.** Attesta hardcodes `idGranularity: "item"`, while Feragame's Passport subject is a lot. UNTP says `idGranularity` and `id` should match the level the Passport was issued at. A per-lot Passport with an item-level `/21/` id is internally consistent only if Attesta treats each lot as a serialised item.
